# Регламент работы с заданиями клиента

Этот регламент обязателен для всех писем и правок по проекту переноса сайтов.

## Получение задания

1. Проверить новые письма клиента и поддержки.
2. Прочитать письмо полностью, включая все вложения и скриншоты.
3. Зафиксировать требования по каждому сайту и не считать письмо закрытым, пока каждое требование не проверено.
4. Создать или обновить строку в [CLIENT_TASK_REGISTER.md](CLIENT_TASK_REGISTER.md) со статусом `Новая`, ссылкой на письмо и финансовой классификацией без указания суммы.
5. Одновременно создать или обновить запись в [client_tasks.json](client_tasks.json). Для статусов `Проверка`, `Клиент проверяет` и `Принято` обязательны поля резервной копии, опубликованного URL, функциональной проверки и скриншотов desktop/mobile.
6. До создания задачи зафиксировать каждое новое входящее письмо через `python tools/email_intake.py` с идентификаторами сообщения и цепочки, временем, вложениями и назначенным ID задачи. Дубликат сообщения не обрабатывается повторно.
7. В начале каждого запуска вывести `python tools/client_task_dashboard.py` и обработать все действия очереди: разобрать новые задачи, продолжить незавершенные, запросить блокирующие данные или сделать корректный follow-up клиенту.
8. В каждом реальном запуске выполнить `python tools/monitor_live_sites.py --fail-on-error` и `python tools/monitor_mail_dns.py --fail-on-error`. При сбое создать техническую задачу в обоих реестрах и начать диагностику; монитор не отправляет тестовые формы.
9. Выполнить `python tools/form_delivery_schedule.py`. Когда проверка доставки просрочена, провести реальную заявку только при доступе к ящику получателя; иначе запросить такой доступ у клиента в исходной цепочке.
10. В первый дневной запуск понедельника сформировать `python tools/weekly_quality_report.py`. Отчет сохраняется локально; клиенту его не отправлять, а сообщать пользователю только о новых рисках или действиях.

## Выполнение

1. Проверить текущее состояние живого сайта до изменения.
2. Создать резервную копию изменяемых файлов и настроек.
3. Внести минимальную безопасную правку.
4. Опубликовать изменение и проверить опубликованную версию.

## Приемка

1. Проверить исходный проблемный сценарий фактически, а не только по коду.
2. Проверить desktop и mobile визуально со скриншотами.
3. Проверить кнопки, формы, обязательность полей, сообщения и отсутствие переполнения.
4. Запустить релевантные тесты и общий smoke-прогон.
5. При обнаружении дефекта вернуться к исправлению и повторять приемку до чистого результата.

## Общение с клиентом

1. После успешной приемки самостоятельно ответить клиенту в исходной переписке.
2. Указывать только реально выполненные и проверенные действия.
3. Если остается внешний блокер, отдельно назвать его и написать, что требуется от клиента или поддержки.
4. Не сообщать о готовности до завершения визуальной и функциональной проверки.
5. Сметы, счета и запросы оплаты вести отдельно от технических отчетов.
6. После отправки отчета записать идентификатор Gmail и сменить статус задачи на `Клиент проверяет`; после ответа клиента - на `Принято` или `Блокер`.
7. Перед письмом клиенту запустить `python tools/validate_client_tasks.py`. Ошибки валидатора означают, что задача еще не готова к отчету.
8. При повторном обращении по уже закрытой задаче пометить ее `reopened`, записать первопричину и добавить регрессионную проверку; без этих полей валидатор не пропустит задачу.

## Закрытие

Задание считается закрытым только после публикации, проверки, фиксации результатов в отчете и реестре, commit, публикации через `powershell -File tools/git_publish.ps1` и уведомления клиента.

## Постпубликационный мониторинг

1. Список контрольных страниц хранится в `monitoring_targets.json` и изменяется только при добавлении, закрытии или смене основного адреса сайта.
2. Монитор проверяет HTTP-код, сетевые ошибки и признаки фатальных ошибок в HTML; результат сохраняется в `output/monitoring/latest.json`.
3. Реальные отправки форм не входят в регулярный мониторинг. Их выполняют при приемке, при инциденте или по отдельному плану проверки доставки, чтобы не создавать лишние письма получателям.
4. График проверок доставки хранится в `form_delivery_checks.json`. После подтвержденного получения обновляют дату проверки и статус доступа к ящику.
5. Критичные MX, SPF и DKIM-записи хранятся в `mail_dns_targets.json` и проверяются командой `python tools/monitor_mail_dns.py --fail-on-error`.

## Непрерывное улучшение

1. Недельный обзор `tools/weekly_quality_report.py` собирает статусы задач, входящую почту, просроченные проверки доставки, возвраты и ошибки QA-гейта.
2. Каждый возврат задачи требует первопричины и регрессионной защиты в `client_tasks.json`; обзор делает такие правила видимыми, чтобы они не были забыты.
3. При повторяющемся инциденте добавить целевой автоматический тест или монитор в том же цикле, а не ограничиваться отчетом.
# Переносимый цикл клиентских задач

## Профиль клиента

Бизнес-правила не хранятся в тексте cron-задачи. Для каждого клиента есть
отдельный JSON-профиль в каталоге `clients/`. В нём перечислены домены,
контакты, варианты названия компании, финансовые признаки, провайдеры и
исключения личной инфраструктуры.

Создание профиля для новой компании:

```powershell
python tools/onboard_client.py --client-id new-client
```

Профиль заполняют фактами из первой переписки: не только адресами, но и
доменами сайтов, компаниями-посредниками и формулировками из подписей.
Поле `mail_lookback_days` задает полное окно для первого сканирования Gmail.
`mail_incremental_lookback_days` задает короткое страхующее окно последующих
проверок; уже известные ID служат границей, поэтому старая история не обходится
заново на каждом запуске.

## Приём писем

Каждое неучтённое Gmail-сообщение сначала проходит через
`tools/client_intake.py`. Маршрутизация использует контекст письма и
вложений, поэтому письмо от нового сотрудника с доменом клиента не теряется.
Результат содержит корзину (`technical`, `finance`, `provider` или
`unrelated`) и список признаков, по которым принято решение.

Технические сообщения создают triage-задачу. Финансовые сообщения фиксируют
статус, но не создают техническую задачу и не инициируют запрос оплаты.
Личная инфраструктура пользователя исключается профилем и не попадает в
клиентские отчёты.

## Автозапуск

Каждый запуск сначала получает детерминированный план поиска:

```powershell
python tools/client_cycle.py --profile clients/ap-real.json
```

Агент выполняет каждый возвращенный Gmail-запрос страницами по ID, читает новые и непрочитанные
кандидаты целиком и передает их в `tools/client_intake.py`. Для уже известных
цепочек указывается существующий ID задачи; для новой технической темы создается
triage-задача. Письма о финансах учитываются отдельно и не превращаются в
технические задачи. До обработки личные исключения из профиля проверяются
первым шагом.

Первый запуск не считает непрочитанное письмо новой ошибкой автоматически:
он сопоставляет его с историей Gmail и реестром. Благодаря этому в работу
попадают новые требования, а подтверждения и уже принятые исправления только
дополняют журнал. Пагинация прекращается на странице, целиком состоящей из
известных ID. После полного прохода без ошибок агент фиксирует маркер:

```powershell
python tools/client_cycle.py --profile clients/ap-real.json --mark-success
```

При ошибке или тайм-ауте Gmail маркер не обновляют: запуск сообщается как сбой,
а не как пустая проверка.

Если ошибка парсинга относится к одному письму, цикл сохраняет его ID в
`unreadable_messages`, продолжает остальные сообщения и повторяет проблемный ID
в каждом следующем запуске. После неудачи обычного чтения цикл использует raw
MIME, пакетное чтение, чтение цепочки и авторизованную браузерную сессию.

В конце московского дня цикл проверяет gate ежедневного отчета:

```powershell
python tools/daily_client_report.py
```

При `due=true` он публикует в рабочий чат фактический итог по письмам, задачам,
QA, ответам и сбоям. После публикации фиксируется единственная отметка за день:

```powershell
python tools/daily_client_report.py --mark-sent
```
