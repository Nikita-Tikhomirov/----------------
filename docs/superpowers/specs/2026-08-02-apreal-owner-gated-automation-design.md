# АП-Риал: автоматизация с двумя шлюзами владельца

## Цель

Автоматизация читает каждое относящееся к АП-Риал письмо, превращает весь запрос и вложения в проверяемое ТЗ, но не начинает работу без одобрения владельца. После выполнения она доказывает каждый пункт ТЗ реальными проверками и снимками, но не создаёт и не отправляет клиенту письмо без отдельного разрешения владельца.

## Неизменяемые правила

1. Письмо не может быть окончательно отложено как «нечитаемое». После ошибок Gmail-коннектора цикл обязан последовательно применить обычное чтение, raw MIME, batch, thread и авторизованный основной Chrome с Gmail.
2. Успешное завершение сканирования запрещено, пока остаётся хотя бы один неразобранный Gmail ID или не достигнута известная граница пагинации.
3. Техническая работа начинается только после явного одобрения владельцем полного ТЗ.
4. Статус готовности запрещён, пока не закрыта вся матрица `требование × сайт` и не приложены функциональные и визуальные доказательства.
5. Черновик, ответ, пересылка, follow-up и финансовое обращение клиенту запрещены до отдельного явного разрешения владельца после проверки итогового отчёта.

## Модель задачи версии 2

Каждая новая техническая задача получает `workflow_version: 2` и проходит состояния:

`new` → `awaiting_user_approval` → `in_progress` → `verifying` → `awaiting_user_release` → `client_review` → `accepted`.

- `awaiting_user_approval`: письмо и вложения полностью прочитаны; составлены ТЗ, список сайтов, критерии приёмки и матрица охвата. Работа не начата.
- `in_progress`: `owner_approval.status=approved` и сохранено доказательство явной команды владельца.
- `verifying`: публикация выполнена; проводится свежая функциональная и зрительная приёмка.
- `awaiting_user_release`: все строки матрицы закрыты, сформированы DOCX/PDF и машинный аудит; внешняя коммуникация всё ещё запрещена.
- `client_review`: допускается только после `owner_release.status=approved` и фактической отправки, подтверждённой Gmail ID и временем.

## Структура ТЗ

`specification` содержит:

- `title` и `source_message_ids`;
- `sites`: полный список затронутых сайтов;
- `requirements`: атомарные требования с ID, источником, областью сайтов и конкретными критериями приёмки; `sites: ["*"]` явно означает все сайты из `specification.sites`;
- `site_matrix`: строку для каждого сочетания требования и сайта со статусом и доказательствами;
- `ambiguities`: только реальные противоречия, которые нельзя разрешить из письма, вложений, истории и текущего состояния сайтов.

Фраза «сделать так же на остальных» разворачивается в явный список сайтов. Закрыть один сайт и отметить всё поручение выполненным невозможно: валидатор требует завершения каждой строки матрицы.

## Доказательства

Для `awaiting_user_release` обязательны:

- резервная копия и опубликованный адрес;
- функциональная проверка каждого требования;
- свежие desktop/mobile снимки для каждого фронтенд-изменения;
- результат сравнения снимка с исходным требованием;
- `evidence_report.docx`, `evidence_report.pdf` и `evidence_report.audit`;
- `owner_release.status=pending` и активный запрет контакта с клиентом.

## Очередь действий

Dashboard выдаёт только внутренние действия:

- `prepare_specification` для нового запроса;
- `request_owner_approval` для готового ТЗ;
- `continue_work` только после одобрения;
- `report_blocker_to_owner` для блокера;
- `request_owner_release` для готового доказательного отчёта.

Ни одно из этих действий не адресовано клиенту. Исторический `client_review` может породить follow-up только для старых задач; у задач версии 2 он дополнительно требует разрешение владельца.

## Автоматизация qa-3

Heartbeat сохраняет полный мониторинг почты и инфраструктуры, но для нового технического письма заканчивает цикл показом владельцу ТЗ и матрицы. Реализация запускается только после последующей явной команды владельца. После реализации heartbeat показывает владельцу доказательный отчёт и ожидает разрешения; отправка клиенту не входит в автономный цикл.

## Критерии готовности

- профиль АП-Риал явно включает двухшлюзовую политику;
- незакрытые recovery-ID блокируют `--mark-success`;
- валидатор отвергает работу без одобрения, неполную матрицу и отчёт без desktop/mobile доказательств;
- dashboard не предлагает обращаться к клиенту в состояниях версии 2;
- текущая портфельная задача переведена в `awaiting_user_release` с путями к проверенному отчёту;
- автоматизация `qa-3` обновлена без отправки какого-либо письма.
